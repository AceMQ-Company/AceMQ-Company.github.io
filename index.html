Runnable, self-contained examples for the Java library — each one compiled and run against a real broker in CI, so none of them rots quietly.

Spring Boot starter v0.3.4

Auto-configuration for the Java library: one connection, a declared topology, annotated listeners, health and metrics — configured from application.yaml. Spring Boot 3 and 4 from one artifact, and the auto-configure module runs on Boot 2.7 as well.

Documentation API reference GitHub

RabbitMQ Admin v0.2.0

RabbitMQ's HTTP management API for Java: users, vhosts, permissions, policies, federation and shovels, health checks, definitions export and import, and the queue facts AMQP cannot report. Deliberately separate from the messaging library, because nothing on a message path should depend on a product-specific management endpoint.

Documentation API reference GitHub Artifacts

Workloads v0.8.4

A load generator for AMQP brokers: a workload DSL, an open-loop rate schedule that measures latency against intended send time rather than actual, and a report that says what it measured rather than what you should conclude.

Documentation API reference GitHub CLI download

AI adapters v0.1.0

A model call that behaves like any other unreliable downstream: rate limits pause the consumer, fatal answers go to the dead-letter queue, a token budget caps spend. Local Ollama by default; OpenAI-compatible and hosted providers with your own key, and an egress guard that keeps everything on the machine when it must.

GitHub Artifacts

Admin MCP server v0.1.0

An MCP server that lets an agent ask a RabbitMQ broker what is going on: queue depth, consumers, bindings, policies and dead-letter backlog, with findings. Read-only tools over stdio, built on RabbitMQ Admin; message bodies never reach the agent.

AMQP for C# and VB.NET from a single assembly, targeting netstandard2.0 so it reaches .NET Framework 4.6.2 as well as .NET Core and modern .NET — the RabbitMQ transport included. Go

AceMQ for Go v0.9.12

AMQP for Go, with a core that has no dependencies outside the standard library — the RabbitMQ transport lives in a subpackage, so a program that only uses the in-memory broker never links an AMQP client. Publishing, consumers that return their disposition rather than calling a method, topology, retries and dead-lettering, tested against a real broker in CI. The envelope is pinned to Java's by the same fixtures the .NET library uses. Connections recover by themselves, and the five extra codec formats are modules of their own so the core keeps one dependency.

Using the Java library

<repositories>
  <repository>
    <id>acemq</id>
    <url>https://acemq-company.github.io/maven/</url>
  </repository>
</repositories>

<dependency>
  <groupId>org.acemq</groupId>
  <artifactId>acemq-amqp-core</artifactId>
  <version>0.7.18</version>
</dependency>
<dependency>
  <groupId>org.acemq</groupId>
  <artifactId>acemq-transport-rabbitmq</artifactId>
  <version>0.7.18</version>
  <scope>runtime</scope>
</dependency>

Both are needed. The transport is discovered at runtime from the amqp:// scheme in your URL, so your code never compiles against it — but without it on the classpath a connection fails with no transport for scheme amqp.
